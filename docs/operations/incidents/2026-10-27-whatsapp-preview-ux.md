# WhatsApp preview and question-shape defects

**Date:** 2026-10-27 (UTC)
**Service:** Render API, direct Meta WhatsApp adapter, ConversationService
**Severity:** Misleading preview and confusing confirmation UX; no case was confirmed in the supplied screenshots

## User impact

In the owner-provided live journey, Agent Zero described “Sinaps Technology” as a company without evidence, then converted “When was it founded?” into “Sinaps Technology was founded on a particular date.” The user was asked to type `SUBMIT` plus an opaque code, and a plain `Submit` did not confirm. The preview had no interactive Submit, Edit, or Cancel controls.

## Cause and boundary

- The “company” classification and claim-preview wording were generated by application-owned conversational copy. They were not evidence of a search or source lookup.
- GPT Luna returned a syntactically populated but semantically unresolved claim containing “a particular date.” The conversation service lacked a guard for placeholder claims and accepted it into an approval preview. This was an application validation gap at the model-to-domain boundary; it does not establish that the model was replaced.
- “When was it founded?” is a question seeking an answer, not a checkable proposition until the entity and source are resolved. The existing phase-one domain represents claim investigations, not source-backed question answering. Converting the question into a placeholder claim obscured that product limitation.
- The current preview-binding design correctly requires approval of the exact preview, but transport code sent only text and did not provide the Meta interactive controls already suggested by the journey. Typing `Submit` without the bound code therefore could not approve it.

## Remediation

- Replace entity-type-specific wording with neutral wording that does not call an unresolved subject a company.
- Reject unresolved placeholder claims before creating a preview; preserve the draft as needing clarification and state that no investigation has started.
- Ask for a public URL or enough context to identify the subject. Keep general profiles and source-backed research questions out of the claim-only workflow until a separate question-shaped research contract is designed.
- Send Meta quick-reply buttons for Submit, Edit, and Cancel. Bind all three action IDs to the displayed preview token; stale controls cannot approve, edit, or cancel a newer preview. Keep text fallbacks for unavailable buttons.
- Parse interactive actions by provider reply ID, not display title, and test long previews so the full text is sent before a separate action-button message.
